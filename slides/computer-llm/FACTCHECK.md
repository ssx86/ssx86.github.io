## 🔴 事实性错误（必须修）

### 1. 第 35 页 · 技能机制讲反了（输出侧截获 vs 实际是输入侧注入）

- **错误内容**：
  - HTML lede：「大模型本身还是只会接龙。但可以给它配一个『外部程序』：模型还是一个字一个字地接，但接出的字连起来有时恰好是一串像指令的话，这时外部程序就认出来，替它去做」
  - 五步流程图：① 接字 → ② 连起来像「去查天气」→ ③ 程序认出这是指令 → ④ 替它查好塞回输入 → ⑤ 接着接
  - 大纲原文：「大模型在接字 → 接出某个词（比如『去查天气』）→ 被外部程序『识别』成指令 → 程序替它去查，把结果塞回输入 → 模型接着接下去」
  - 结论框：「技能没有打破接龙——它是在接龙外面套了一层帮手」

- **为什么错**：
  Skill（技能）的核心机制是**输入侧的动态注入**，不是输出侧的截获。一个技能本质上是**一份说明文档**（`SKILL.md` + 可选脚本），写在文件系统里。当对话内容匹配到这个技能的适用场景时，运行时（外部程序）会**把这份说明文档的内容动态拼进大模型的输入/上下文里**。模型读了这份说明书，才知道"我有这个能力、什么时候该用、怎么用"，然后照着说明去行动。

  方向是：**输入被增强**（悄悄塞进一段技能说明），不是**输出被外部程序截获**（模型接出指令词被认出来）。

  另外，即使把这段描述往"工具调用（function calling / tool use）"上靠，也不准确：现代工具调用是模型经过训练后**结构化地决定**调用某个工具（输出 JSON 工具调用），而不是"接字连起来恰好像指令"。所以这个描述既不是 skill，也不是准确的 tool use，是两者的混说且方向反了。

  更关键的是：**P36 演示装的 html-ppt 技能，恰恰是输入侧机制的真实例子**——装完技能后，SKILL.md 被注入上下文，模型读了才知道怎么做 PPT。P35 的错误描述和 P36 的真实演示是自相矛盾的。

  （参考：Claude Code 官方文档与多个技术分析均确认 skills 是"加载进上下文窗口""塑造模型如何思考"，而非"在模型外截获输出"。）

- **对小白的影响**：
  小白会形成"技能 = 模型无意中说出指令被外部程序抓住执行"的错误认知。这会让人以为模型是"碰巧"触发技能，而不是"读了说明书主动使用"。更重要的是，它和紧接着的 P36 真实演示（装技能 = 装一份说明）对不上，会让认真看的人困惑。

- **正确应该怎么讲**（小白版）：
  把五步流程改成"输入增强"方向：

  1. 技能 = 一份**说明书**（写清楚"你能做 X、什么时候做、怎么做"）
  2. 说明书平时不在对话里，存在电脑上
  3. 当你聊到相关的事，**运行时悄悄把这份说明书塞进大模型的输入里**
  4. 大模型**读了说明书**，就知道"哦，我有这个能力，现在该用它了"
  5. 然后照着说明书去做（接龙还是接龙，只是输入里多了一段说明）

  一句话表述：「**技能没有打破接龙——它是在大模型的输入里，悄悄多塞了一份说明书，让模型知道自己多了个本事**」。

  这样既保留了 PPT 想强调的"没有打破接龙"结论，方向又是对的（输入增强），且和 P36 演示（装技能 = 装说明书）完全对得上。

### 2. 第 37 页 · 技能卡继承 P35 的错误表述（同源）

- **错误内容**：
  - HTML 技能卡：「🛠️ 技能 — 接龙外面的帮手程序」
  - 大纲：「技能：接龙外面的帮手程序」

- **为什么错**：
  "接龙外面的帮手程序"这个表述继承了 P35 的错误框架（暗示是输出侧的外挂程序）。虽然字面上"帮手"不算全错，但它没有点出技能的本质是**输入侧的说明书注入**，会强化 P35 的错误认知。

- **对小白的影响**：
  P37 是收尾串概念页，是小白最后记住的样子。如果这里不改，即便 P35 改了，小白记住的还是"技能 = 外面挂的程序"。

- **正确应该怎么讲**：
  改为：「🛠️ 技能 — 悄悄塞进输入的说明书（让模型多一个本事）」或「🛠️ 技能 — 装进上下文的能力说明书」。
  必须和 P35 修正后的表述保持一致。

### 3. 第 28 页 · "关键信息放开头"与第 12 页自相矛盾

- **错误内容**：
  - HTML 卡片①：「**关键信息放开头，因为最早的最容易被丢**」
  - HTML 逐字稿：「第一，关键信息放开头。因为最早聊的最容易被丢，但你把重要的放最前面，反而……不对，应该说，重要的信息要在对话里反复出现，不容易被挤掉。」
  - 大纲：「① 关键信息放开头」

- **为什么错**：
  P12 明确教过：上下文盒子装满时，**最早（最左边）的内容会被丢掉**（SVG 里最左色块标"可能被丢掉"，底栏"旧内容在左边会被丢"）。

  按这个机制，"把关键信息放开头"= 放在**最早**= 放在**最容易被丢**的位置。理由"因为最早的最容易被丢"和动作"放开头"是**直接打架**的——你不可能因为"它最容易被丢"所以"故意放在那"。

  逐字稿里那句"反而……不对"恰恰暴露了作者自己也意识到逻辑不顺，只能临场改口，但**卡片上印的还是错的版本**。小白照卡片做，等于把最重要的信息放在最先被丢弃的地方，适得其反。

  （注：提示工程里确实有"放开头/放结尾"的建议，但那是基于"中间迷失"注意力现象，针对的是**单条提示内部**的位置，和上下文截断无关。这里的理由写的是截断，所以是错的。）

- **对小白的影响**：
  小白会得出"重要的放前面能保护它"的反向认知，实际操作中把关键信息放到最先被丢弃的位置，越聊越丢。

- **正确应该怎么讲**：
  三选一：
  - **改动作**：① 重要的事，在最近的对话里**再提一次**（别指望它记得很久以前的话）→ ② 必要时重复 → ③ 放进设定层
  - **改理由**：如果想保留"放开头"，理由必须改成针对单条提示的"模型对开头更关注"，但这对小白反而更绕，不推荐。
  - **直接删①**：因为动作②（重复）和动作③（设定层）已经覆盖了正确的策略，① 是多余且矛盾的。

  推荐改动作：把①改为「**重要的事，需要时再提一遍**（别指望它记得前面说过）」，和②③方向一致。

## 🟡 例子不当（应该改）

### 1. 第 11 页 · 多轮对话例子选错（自包含问题，体现不出历史必要性）

- **当前例子**：
  - 🧑 第一轮：你好
  - 🤖 第一轮：你好！有什么可以帮你？
  - 🧑 第二轮：（前面说过的话）+ 今天北京天气
  - 🤖 第二轮：北京今天晴天

- **为什么不当**：
  这一页要讲的核心是："第二轮必须带上历史，否则进行不下去"。但"今天北京天气"是一个**自包含的单轮问题**——就算把第一轮"你好"那段历史全丢掉，第二轮照样能回答。这个例子恰恰**体现不出"历史被带上"的必要性**，论证失效。

  还有个附带问题：大模型本身并不知道实时天气，"北京今天晴天"很可能是它**编出来的**。用一个可能是幻觉的答案来举例多轮对话，反而添乱。

- **更好的例子**（必须指代前文才能回答）：
  - 🧑 第一轮：我叫小明
  - 🤖 第一轮：你好，小明！
  - 🧑 第二轮：（前面说过的话）+ 我叫什么名字？
  - 🤖 第二轮：你叫小明

  如果第二轮丢掉历史，只剩"我叫什么名字？"，模型根本没法回答——**这就真正体现了"历史必须带上"**。小白一眼就能看懂：丢了历史，它就答不出。

  （可选第二轮替代："我刚才说的那个人，是哪里人？"——同样必须依赖前文。）

---

### 2. 第 14 页 · 幻觉反例太抽象，没有具体实例

- **当前例子**：
  - 左框 ✅（正例）：「故宫在____」后面常跟「北京」→ 填「北京」（对）
  - 右框 ❌（反例）：「也照『最顺口的接法』填一个看起来像答案的假东西（错）」

- **为什么不当**：
  这页的意图是"一正一反"对比，正例给了具体内容（故宫→北京），反例却只给了一句抽象描述"填一个看起来像答案的假东西"，**没有任何具体实例**。小白看了正例能懂"规律它见过"，但反例抽象得没法对应——没有具体的"假东西"长什么样，"会胡说"这个观点就立不住，对比的说服力大打折扣。

- **更好的例子**：
  反例给一个具体的、一眼能看出是编造的场景。比如：
  - 右框 ❌：问它「苏轼的妹妹叫什么名字？」→ 它言之凿凿地编出「苏小妹，嫁给了秦观……」（其实"苏小妹"是文学虚构人物，历史上不存在）

  或者更直白：
  - 右框 ❌：问它「爱因斯坦 1925 年在清华的演讲讲了什么？」→ 它给你编出一段演讲内容（其实这事根本没发生过）

  关键是：反例必须有一个**具体的、小白能立刻判断为假**的内容，才能让"它会一本正经胡说"这个观点真正落地。

## 🟢 表述可优化（不致错但不严谨）

### 1. 第 9/13 页 · "整个互联网"略夸大（HTML 丢了"几乎"）
- **问题**：P9 保留了"几乎整个互联网"，但 P13 的 HTML 视觉框（`整个互联网的文字`）和 lede（`把「读过」整个互联网……`）都把"几乎"丢了，变成"整个互联网"。训练数据是互联网抓取的子集 + 书籍 + 代码等，远非"整个互联网"。
- **是否误导**：P13 紧接着说"不像人那样理解内容，只记规律不记事实"，自我修正了"它什么都知道"的风险。所以是可接受的简化，但 HTML 丢了"几乎"让表述更绝对，建议补回"几乎"或改"海量互联网文字"。

### 2. 第 30 页 · "查到的是真的"略绝对
- **问题**：HTML 卡片「查准确事实 → 用搜索，查到的是真的」。搜索结果也不一定全真。
- **是否误导**：方向是对的（查事实用搜索而非让模型猜），但对小白说"查到的是真的"可能形成"搜索 = 一定真"的过度信任。建议改"查到的是**原始来源**，可核实"。

### 3. 第 34 页 · "不用记命令"与第 36 页展示命令略有张力
- **问题**：P34 说 ZCode「不用记命令、不用懂代码」，但 P36 立刻展示 `npx skills add ...` 这条命令。
- **是否误导**：P36 已加安抚句"看不懂没关系……现场敲给大家看"，化解了大半。严格说"不用记命令"指的是日常使用是 GUI 驱动，不是零命令。可接受，但可改为"**平时**不用记命令"。

### 4. 第 33/34 页 · ZCode vs Claude Code 对比略简化
- **问题**：PPT 把 ZCode（桌面应用）和 Claude Code（命令行）对立起来。实际上 ZCode 是一个 Agentic Development Environment，**可以可视化管理 Claude Code、Codex、Gemini CLI 等多个 CLI agent**——也就是说 ZCode 能"装着"Claude Code 跑。
- **是否误导**：对小白来说"桌面 GUI vs 命令行"是有效且有用的对比框架，可接受。但严格讲两者不完全是替代关系。如要严谨，可在 P34 备注里加一句"ZCode 其实也能在里面调 Claude Code"，但对小白可能反而绕，建议保持现状或仅口头提一句。

### 5. 第 36 页 · "调用技能"口语化
- **问题**：P36「说一句『帮我做一份 PPT』→ 看它**调用技能**生成」。严格说技能不是被"调用"（call），而是被"注入上下文"后模型主动使用。
- **是否误导**：口语里"调用技能"是可接受的简化，小白能懂。但如果 P35 按前述修正改成"输入侧说明书注入"，这里的"调用"最好也同步软化为"用上技能"或"靠技能来做"，保持术语一致。

### 6. 第 11 页 · 天气答案可能是幻觉（附带问题）
- **问题**：见 🟡-1。即便不改成"我叫小明"的例子，"北京今天晴天"也极可能是模型编的（模型无实时天气能力），用一个幻觉答案来演示多轮对话，本身就不合适。
- **处理**：随 🟡-1 一并改掉即可。

## 总评

### 整体技术准确性
**大部分机制讲得准确**，主线（输入输出盒子 → 故事接龙 → 上下文 → 训练 → 幻觉 → 输入是唯一依据 → 七个对话动作）的认知阶梯是扎实的，核心心智模型（接龙、概率续字、只记规律不记事实、会顺着语气、会忘）都讲对了方向。P1–P27、P29–P34、P38 基本没有机制性错误，是一份质量不错的科普。

### 最需要修的（按优先级）
1. **P35 技能机制讲反**（🔴 最严重）：核心概念错误，方向反了，且与 P36 真实演示矛盾。这是全篇最该改的地方。修正方向：从"输出被外部程序截获"改为"输入被悄悄注入说明书"。P37 同步修正。
2. **P28 放开头逻辑矛盾**（🔴）：与 P12 直接打架，逐字稿已暴露"不对"的口误。改动作或改理由，建议改动作为"需要时再提一遍"。
3. **P11 多轮对话例子**（🟡）：自包含问题，论证失效。改成"我叫小明→我叫什么名字"这类必须依赖前文的例子。

### 对两个已知问题的核查结论
- **Skill 机制（P35）**：**确认错误**。用户指出的方向完全正确——skill 是输入侧的说明书注入，不是输出侧的截获。我额外发现：即便往 tool use 上靠也不准确（tool use 是结构化调用，不是"字连起来恰好是指令"），且 P35 的错误描述与 P36 真实演示（装 SKILL.md）自相矛盾。P37 收尾卡也继承了错误表述，需同步改。
- **多轮对话例子（P11）**：**确认不当**。"今天北京天气"是自包含单轮问题，丢掉历史照样能答，体现不出"历史必须带上"。附带问题：答案可能是幻觉。建议改成"我叫小明 → 我叫什么名字"。

### 修复优先级建议
- 必改：P35（含 P37 同步）、P28、P11 —— 这三处会直接形成错误认知或让小白做反。
- 建议改：P14 反例补具体实例 —— 提升说服力，但不算硬错误。
- 可选优化：6 项 🟢，按精力处理，不影响整体正确性。
